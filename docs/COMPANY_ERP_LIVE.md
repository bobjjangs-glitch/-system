# 회사 닷홈 ERP 연결 — Android 1.10.0(20)

회사 ERP `https://bobjjangs1231.dothome.co.kr/tire/erp/index.php`의 거래처·품목·확정 판매전표 조회와 **앱에서 새 판매전표 작성**을 지원합니다. E카운트 Open API와 별도이며 E카운트 인증 정보는 필요하지 않습니다.

사용자의 공개 [ERP 소스](https://github.com/bobjjangs-glitch/erp)에서 DB·권한·전표번호 발급 방식을 확인했습니다. 실제 닷홈의 인증된 자료·FTP·Render 환경변수에는 이번 작업 환경에서 접근할 수 없어 **실제 서버 설치·배포·원본 대조는 별도로 필요합니다.** 인증 없이 조회한 주소는 HTTP 401을 반환하므로 실제 품목 오류의 인증된 응답까지 확인했다는 의미는 아닙니다.

## 업데이트와 설치

기존 ERP와 DB를 백업하고 ZIP의 폴더 구조대로 다음 **다섯 PHP 파일을 함께 추가/교체**합니다.

```text
tire/erp/dispatch_api.php
tire/erp/dispatch_setup.php
tire/erp/dispatch_sale.php
tire/erp/inc/dispatch_bridge.php
tire/erp/inc/dispatch_sales.php
```

기존 `inc/config.php`, 회사 데이터, 연결키 파일은 ZIP에 들어 있지 않습니다. 패키지는 `python3 scripts/package-company-erp.py <출력.zip>`으로 만듭니다.

1. ERP **관리자**로 [배차 연결 설정](https://bobjjangs1231.dothome.co.kr/tire/erp/dispatch_setup.php)에 로그인합니다. 기존 연결키는 유지하고 처음 연결할 때만 **연동키 발급**을 누릅니다.
2. 같은 페이지에서 **앱 판매 작성 허용 · 저장소 준비**를 누릅니다. 기존 키를 유지하며 중복 방지 테이블과 배송정보·품목 메타데이터 열을 추가합니다. ERP DB 계정에 CREATE/ALTER 권한이 필요합니다. 판매 작성 기록에는 이 설정을 수행한 ERP 관리자 계정이 사용됩니다.
3. Render `bareun-dispatch-test` → **Environment**의 아래 값을 확인합니다. 기존 값이 정상이라면 그대로 사용합니다.

| 변수 | 값 |
| --- | --- |
| `COMPANY_ERP_API_URL` | `https://bobjjangs1231.dothome.co.kr/tire/erp/dispatch_api.php` |
| `COMPANY_ERP_TOKEN` | ERP에서 발급한 기존 연결키 |

4. 필요한 기존 무료 서버 자료를 백업하고 `codex/free-node-test` 최신 커밋을 **Manual Deploy → Deploy latest commit**으로 배포합니다. 카페24에서는 동일 환경변수와 영속 `APP_DATA_DIR`을 설정하고 PM2를 재시작합니다.
5. Android 1.10.0(20)를 설치하거나 웹을 새로고침합니다. **연결 상태 새로고침 → 품목 목록 가져오기**로 실제 조회 성공을 확인하고 알려진 거래처·품목·전표를 ERP 원본과 대조합니다.

키를 재발급하면 이전 키가 차단되므로 Node 서버도 갱신해야 합니다. `inc/dispatch_bridge.private.php`는 키 해시·ERP 식별자·판매 작성 설정을 보관합니다. 삭제하거나 공개 저장소에 올리지 마세요. 앱과 공개 다운로드에는 연결키를 포함하지 않습니다.

## 새 판매전표 작성

회사 ERP가 연결된 상태의 **배송지 직접 입력**은 새 ERP 판매 작성 화면입니다. 거래처 검색에서 선택하면 거래처명·주소·연락처가 채워지며 배송정보는 수정할 수 있습니다. 거래처의 기본 소매·도매 구분에 맞는 ERP 단가를 사용합니다. 행의 **+**로 ERP 품목을 선택하고 표를 좌우로 밀어 입력합니다.

| 항목 | 처리 |
| --- | --- |
| 품목코드·품목명·패턴 | ERP 검색 결과를 채웁니다. 이름·패턴은 전표용으로 수정할 수 있습니다. ERP 품목 자체는 수정하지 않습니다. |
| 수량 | 양수, 소수점 세 자리까지 입력합니다. |
| 단가·금액·합계 | 단가와 금액은 공급가액 기준, 합계는 부가세 포함 원 단위입니다. 마지막으로 편집한 단가/금액/합계를 계산 기준으로 보존합니다. |
| 비고·DC율 | 비고는 ERP 품목 메모에 저장합니다. DC율을 변경하면 ERP 기준가 **공장도가(있는 경우), 없으면 소매 기준가**에서 할인한 단가를 계산합니다. 기준가가 없으면 단가를 직접 입력합니다. |

합계 540,000원, 수량 12개를 직접 입력하면 공급가액 490,909원·부가세 49,091원·표시 단가 40,909원으로 보존합니다. 행별로 원 단위 반올림한 금액을 합산합니다. 기존 ERP에서 가져온 전표는 원본 총액을 유지하며 ERP 연결 배송지의 기존 품목·금액을 편집해 ERP 원본을 덮어쓰지 않습니다.

**ERP 판매·배송지 함께 저장**을 누르면 다음 순서로 처리합니다.

1. ERP 서버의 `Asia/Seoul` **오늘 날짜**와 실제 저장 순서로 `YYYYMMDD-순번`을 발급합니다. 화면 번호는 예약되지 않은 예상값입니다. ERP의 기존 `SL` 날짜별 카운터와 당일 실제 판매번호의 최댓값을 함께 확인합니다. 기존 번호는 바꾸지 않습니다.
2. ERP에 **작성중(`draft`) 판매전표**와 품목을 저장하고 감사 기록을 남깁니다. 판매 확정·재고 차감·수금은 기존 ERP에서 처리합니다.
3. ERP가 발급한 번호와 날짜로 앱 배송지·업로드 내역을 생성합니다. 날짜가 바뀐 뒤 저장하면 ERP가 발급한 실제 날짜로 저장됩니다.

거래처·품목은 활성 ERP 검색 결과에서 선택해야 합니다. 코드를 직접 바꾼 행은 다시 검색해 올바른 품목을 선택하세요. ERP 연결이 없는 환경의 직접 입력은 기존 배송지만 저장하는 기능을 유지합니다.

## 연결 오류와 저장 복구

서버는 ERP 호출 전에 요청 번호와 입력 내용을 영속 DB에 보관합니다. ERP는 같은 요청 번호의 재시도에 원래 전표를 반환합니다. 응답 유실·로컬 파일 저장 오류가 발생해도 **같은 전표에서 다시 저장**하거나 **마무리할 ERP 판매 저장 → 이 전표 저장 마무리**로 이어서 처리하세요. 확인 중인 전표는 필드를 잠가 내용을 바꾼 별도 요청을 보내지 않습니다. ERP가 입력 오류로 저장하지 않았음을 확인한 경우에는 수정할 수 있습니다.

ERP와 앱 DB는 별도 서버이므로 하나의 DB 트랜잭션으로 묶이지 않습니다. ERP 저장 후 앱 저장이 실패하면 복구 목록에 남습니다. **`APP_DATA_DIR`과 ERP DB를 보존해야 복구가 가능합니다.** 무료 Render 임시 DB가 재배포로 지워지면 진행 중 요청 정보도 사라질 수 있습니다. 그 경우 ERP 판매내역을 먼저 확인하세요. 앱 배송지를 삭제해도 ERP 판매전표를 자동 삭제·취소하지 않습니다.

현재 ERP의 실제 번호 카운터가 공개 소스의 `SL`과 다르게 수정되어 있다면 기존 ERP의 번호 발급 로직도 함께 확인해야 합니다. 서로 다른 시스템이 같은 날짜 순번을 쓰는 경우 번호 형식만 바꾸어서는 동시 저장 순서가 보장되지 않습니다.

## 거래처·품목·기존 판매 조회

- **거래처 목록 가져오기 / 품목 목록 가져오기**와 직접 입력의 검색은 실행할 때마다 ERP를 조회합니다. 파일 창을 열지 않습니다. 거래처 주소·전화, 품목명·규격·패턴·코드·단가·과세정보를 가져옵니다. 원가·계정·은행정보는 가져오지 않습니다.
- **판매 조회 일자 → 판매조회 내역 가져오기**는 DB 판매일자로 작성중·확정·취소 전표를 목록으로 읽습니다. `20261106-48`, `26/11/06-48`을 해석합니다. 전표번호를 눌러 전체 명세서를 보고 선택한 전표만 배차 대기에 등록합니다. 새 판매전표를 ERP에 중복 생성하지 않습니다.
- 취소·반품/0 이하 수량 전표도 목록과 명세서에는 보이지만 배차 선택은 막습니다. 작성중 전표는 상태를 명시하고 선택할 수 있으며 ERP 판매 확정·재고 차감을 진행하지 않습니다. 선택 직전에 ERP를 다시 읽어 수정·취소를 검증합니다.
- 이미 등록한 전표는 회색 선택 상태로 표시하고 반복 등록하지 않습니다. 선택하지 않은 전표는 목록에 유지합니다. 배송주소·연락처·요청사항 보정은 앱 배송지에만 적용합니다. 기존 1.9 클라이언트의 `/sales/fetch`는 기존 확정 전표 검토 방식을 유지합니다.
- 모바일 명세서에는 공급자/공급받는자, 전표번호·일자·상태·판매구분·결제방법·고객명·차량번호, 배송정보, 품목코드·품명·규격·패턴·수량·원본 단가·공급가액·합계·적요·공장도가·DC율, 전표 공급가액·부가세·합계를 표시합니다. 미등록 값은 추정하지 않습니다. [상세 안내](COMPANY_ERP_SALES.md)를 참고하세요.
- PDO가 숫자를 문자열로 반환하는 안전한 경우만 정규화합니다. 계약 필드가 없으면 필드 이름을 포함한 오류를 표시합니다. 실제 오류 응답에 따라 파일 누락·다른 ERP 구조·인증 오류를 추가 확인해야 할 수 있습니다.
- 목록은 모든 페이지의 변경 표식을 확인하고 완전히 읽은 뒤 교체합니다. 최대 **100,000개** 검색 자료, 한 번에 2,000개 판매전표, 페이지당 10,000개 품목, 조회 전체 45초 한도입니다. 실패 시 이전 자료를 실시간 결과로 표시하지 않습니다. 검색은 최대 30개입니다.
- 연결키는 Node 서버에서 HTTPS 헤더로만 보냅니다. 조회 API는 읽기 전용 트랜잭션이며 판매 작성은 별도 `dispatch_sale.php`에서만 허용합니다. 기사는 ERP 조회·작성 API를 사용할 수 없고 배송 품목의 단가·금액·할인·ERP 내부 ID도 전달받지 않습니다.

## 검증 범위

PHP 8.3.36 + MariaDB 10.11에서 공개 ERP의 실제 테이블 DDL과 가상 자료로 관리자·CSRF 설정, 기존 키 유지, 품목 조회, ERP·배송지 저장, 원 단위 합계 보존, 다섯 동시 저장의 연속 번호, 응답 유실 재시도, 잘못된 품목의 롤백, 로컬 저장 실패 복구, 기사 권한과 재고 미변경을 검증했습니다. 휴대폰 크기의 브라우저에서는 거래처 선택·표 입력·저장 결과를 확인했습니다. 자동 서버 테스트는 응답 형식·계산·중복·오류 복구를 포함합니다.

가상 자료 검증은 실제 회사 ERP 설치·실제 자료 대조·Galaxy A16 설치 검증을 대신하지 않습니다. 실제 ERP 구조가 공개 소스와 다르면 배포된 구조에 맞게 조정해야 합니다.
